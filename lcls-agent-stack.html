LCLS Agent Stack
Proposal · AI4SO · LCLS · October 2026

Bring tools to AIs. Authorize at the tool.

We make agents more resourceful by bringing tools to them, and we check access at the tool, on every call, for the person asking. In this proposal one access interface on S3DF does that check, so a harness can run anywhere; and when agent use scales up to goal campaigns, where many agents work toward one checkable goal, every agent's call still passes the same check. Cogito, SLAC IT's hosted agent service, is the recommended way to run agents: today for people who already work on S3DF, and for everyone once its sessions call the interface.

Front end · not a layer

Where a person starts: a terminal, Cogito's web page, or a GUI's Agent button.

1 · Harness

Runs the loop: Claude Code or opencode for agents, a workflow engine for fixed workflows.

2 · Application

The unit a developer ships. It consists of features; every agent is one.

3 · Feature

Know-how for one use case, written as a skill. Uses at least one tool.

4 · Tool

The only layer that touches a resource, so access is checked here, at the access interface.

Who are you?

S3DF Dex, the S3DF sign-in service, signs you in.

May you?

pief-authz decides: built for pief's new eLog (dev), proposed for the rest.

Then

The access interface, this page's proposal, enforces that, runs the tool and audits the call; the resource checks you again.

Terms used on this page

S3DF is SLAC's shared compute and data facility. EPICS PVs are the control system's process variables. MCP is how a harness calls remote tools. The access interface (the authorized-access interface) is this page's proposal: one service on S3DF that hosts the tools and checks every call. S3DF Dex is S3DF's sign-in service. pief-authz is SLAC's new authorization service (OpenFGA behind the AuthZEN API), built with pief, SLAC's new eLog; today it answers only for pief's own eLog, on a dev deployment. The PV Gate is a separate proposal for EPICS PVs. More in Appendix I.

Overview

What are the layers, and which unit does a developer ship?

A person starts at a front end, which is not a layer. A harness loads an application, which consists of features, and each feature uses at least one tool. In this design, developers always ship an application, never a bare skill or a harness.

Why authorize at the tool

  • Every path ends in a tool. The layers above multiply, but they converge on a short list of tools, so one check there covers every combination.
  • The layers above can be skipped. They are files in a harness the person controls; a rule in a feature is text the model may not follow.
  • Some credentials do more than the tool. A personal Jira token carries full account rights, so it stays behind the tool that narrows it.

The full argument: Appendix A. How the diagram maps to the roadmap: Appendix G.

1 · Harness

The program that runs the agent loop: it talks to the model, keeps the session and sends tool calls. Claude Code (as claude-lcls, or in Cogito) and opencode run open-ended agents. A workflow engine runs fixed workflows: LangChain, or a saved workflow run headless.

In this design, a harness holds no rights to LCLS resources of its own, and any harness can load any application.

2 · Application

What a developer ships: a purpose, instructions and features. It names the tools its features use but does not carry them; each tool is built once, by whoever owns its resource, and runs behind the access interface. Every agent is an application, and developers always ship an application, never a bare skill or a harness.

Small: the AMI agent, one feature. Large: Hutch Copilot, six features, three of them reused.

Open-ended agent or fixed workflow

Who picks the next step: the model, or the code (reference 11)?

  • Open-ended agent: bring tools to the AI. The model picks tools as it goes, so every tool added helps. Hutch Copilot and the AMI agent.
  • Fixed workflow: bring AI into a tool. The code runs set steps and a model fills one, as in retrieval-augmented generation (RAG): fetch log lines, then summarize. It is predictable; with its tools restricted, the model cannot reach past it. The DAQ debug and eLog grubber agents.

Both would call tools through the same access interface, with the same authorization, audit and approval of writes, once a launched workflow carries the person's session token rather than the GUI's account (Appendix E).

3 · Feature

Written know-how for one use case, such as DAQ diagnosis: which tool to use and how to read its answers. Features are shared: Hutch Copilot reuses the other three agents' features.

Today an LCLS skill bundles a feature and a tool in one folder. In elog-search, the SKILL.md is the feature (when and how to search the eLog) and the script next to it is the tool (the call to the logbook API). This design moves the script behind the access interface.

4 · Tool

One callable that reads, or proposes a change to, one resource: elog-search reads the eLog, EPICS PVs reads process variables and proposes PV changes. The only layer that touches a resource, so the one that checks who is asking.

This generalizes the EPICS PV gateway, where a gateway and IOC access security decide per PV what any client may read or write: here EPICS PVs are one tool among many (Appendix B). Diagram 2 shows the check.

At the tool layer. Every call passes the access interface on S3DF, for the person asking, before the tool touches its resource. Three parts answer three questions:

QuestionWho answers itToday

Reads then run at once, as you; writes become proposals a person approves. One write is drawn (a PV put); an eLog post or a Jira comment takes the same lane.

Your session

A harness on a VM or a laptop, running any application. It holds a Dex session token meant only for the interface, never a resource credential. Cogito joins this path once its sessions can get one (Diagram 4).

S3DF Dex: sign-in

Dex issues and signs the tokens that name you; pief, and the interface, read that name as user:slac/<you>. The interface only verifies a token (signature, issuer, audience, expiry), as pief does, so the same S3DF identity names you to both; each should still take a token issued for it (Appendix E). Built: pief and elog-search already rely on Dex tokens.

The access interface

The enforcement point: one service on S3DF that hosts the tools, the tool layer's front door rather than a fifth layer. On every call it authenticates you, applies its agent rules (catalog, lane, arguments), asks pief-authz and writes an audit record. On deny it runs nothing and tells the agent which check failed. It is a proposal.

pief-authz: authorization

The decision point. On every call that passes its agent rules, the interface would ask pief-authz whether this person may use this resource; it answers allow or deny over the AuthZEN API. Its design records name other services as its next callers (Appendix L).

ResourceWhat pief-authz would decideToday
eLog logbooksMay you read, or post to, this logbook?Built, dev only. For the legacy eLog an extra check: a deny is final
EPICS PVsMay you read, or propose a put, in this hutch's PV area?New type needed (Appendix M)
Jira, Confluence, Slurm, DAQ logs, Grafana and the restMay you use this tool through the interface?New, coarse types needed; each resource still decides the rest

Tool grants would be coarse: a resource's Unix groups (which needs pief's group sync, off on dev since 13 October 2026), or every S3DF user for tools such as Jira. They only gate the tool.

Open: services outside pief's own cluster cannot call pief-authz yet (issue #482). Lanes, arguments and the decision log stay in the interface.

Read lane: the per-user runner

Read tools run at once, as you: the runner (a proposal) runs the tool as your Unix account on S3DF, with your own credential, so each resource applies its own rules again. The session never sees that credential. Why a runner, and the other back ends considered: Appendix H.

Propose lane: approvals

A write tool becomes a proposal (this lane is itself a proposal). An agent rule, such as a PV step limit, can reject it at once, before anyone is asked; otherwise it waits in the approval console. For a PV put, the control room decides: the operator on shift. pief-authz only answers whether you may propose one, never who approves it. For an eLog post or a Jira comment, the person who asked or the shift lead decides. Only after approval does a write service, the part of the interface that performs approved writes, act.

Resources and their credentials

Each tag names what the runner uses: your own token for the legacy eLog (elog-search), pief's logbook (the pief CLI), Jira and Confluence; a Unix group for the DAQ log index; your account for Slurm. The two eLog tools differ (Diagram 3). EPICS PVs go through the PV Gate: reads through a read-only gateway, puts only after approval. Appendix C lists each tool with its evidence.

The expert path

Run the harness on an S3DF interactive node, where the skills' shell commands already reach every resource as you. It works today, gives a full shell and is the fastest loop for building tools. It gives up the interface's checks, audit and propose lane, leaves your token files where the agent can read them, and reaches live EPICS PVs only through an operator session (Appendix D).

Overview

How does a harness on a VM search the eLog for a user?

Steps 1, 2, 3 and 5 are the same for both tools. Step 4 differs: 4a is elog-search on the legacy eLog, today; 4b is the pief CLI on pief's logbook, on dev. Your own S3DF tokens go only from the runner to the eLog; they never reach the VM or the harness.

The interface and the runner are proposals; S3DF Dex, the legacy eLog and pief (on dev) exist. Who answers which question, in one table: Appendix L.

1 · Ask

You run Claude Code on your VM with Hutch Copilot and ask what sample was in run 42 of mfx000000026 (an example id). Its Experiment Q&A feature has the model call the eLog search tool, and the harness sends that call to the access interface with a session token meant only for the interface (Appendix E). The VM holds no eLog credential.

2 · Check

The interface checks the token's signature against S3DF Dex's published keys, plus its issuer, audience and expiry, and reads your user name: user:slac/<you>. It applies its own agent rules: the tool is in the catalog, it is a read tool, and the arguments are valid. Then it asks pief-authz whether you can_read_entry on logbook:experiment/mfx000000026, the experiment the call names; a search across experiments would use pief-authz's resource search, as pief's logbook does. On deny, it runs nothing and tells the agent which check failed.

Until pief replaces the legacy eLog, this check is extra: in path a the legacy eLog checks an allow again, but a deny is final, so where pief's roles are narrower the interface can refuse a read the legacy eLog would allow. It asks anyway so that every tool gets the same person-and-resource gate, recorded in the audit log, before anything runs.

3 · Run

The per-user runner runs the tool as your Unix account on S3DF: elog-search for path a, or the pief CLI for path b. Which tool answers an eLog search is a catalog choice; until pief replaces the legacy eLog, it could offer either. Each finds your own token in your S3DF home, where you put it with s3df login or pief login.

4a · elog-search reads the legacy eLog

elog-search calls the legacy eLog API on pswww with your own S3DF token, the one s3df login writes; it has no shared-account fallback. The legacy eLog lists the experiments your roles let you read, and elog-search searches only those; its scope line says so ("readable as <you>"). The legacy eLog does not ask pief-authz. This step works today, from an S3DF node.

4b · pief reads its own logbook

The read-only pief CLI calls pief's logbook (dev) with the token from pief login. The logbook verifies it against Dex, asks pief-authz, as service:pief-api, which logbooks you can read, and returns only entries from those. The same reads are MCP tools at /mcp.

pief holds a synced, read-only copy of the legacy entries, and its roles are copied with differences, so the two paths can return different entries.

5 · Audit and return

The interface records who called which tool with which arguments, the pief-authz decision and how many entries came back (pief keeps no record of decisions), then returns the entries. Your S3DF tokens never reach the VM or the harness.

    A. Why access is checked at the tool, not the feature or the application
    
      
      
      "At the tool" means: each tool runs on S3DF behind one access interface, and every call to it is checked there, for the person asking, before the tool touches its resource. The resource then applies its own rules as well. The interface is the tool layer's front door, not a fifth layer.
      
  
      
    
      Every path ends in a tool. Harnesses, applications and features multiply and combine: several front ends and harnesses times many applications times shared features. They all converge on a short list of tools, and only a tool touches a resource. Fixed workflows launched from an Agent button are no exception. One check there covers every combination, including ones nobody has built yet.
      
    
      The layers above can be edited or skipped. An application and its features are files that run inside a harness the person controls. A rule written in a feature is text the model may not follow; the LCLS workflow map notes that the Slurm skill's "read-only" promise is prompt text only. A check in the harness exists only in that harness: Osprey, an EPICS agent toolkit from Berkeley Lab's ALS, puts its write approval in a Claude Code hook, so other MCP clients likely get no approval step. Since any harness can load any application, a check above the tool is a check some path does not have.
      
    
      Some credentials can do more than the tool does. The Jira skill says it plainly: "The token is not read-only — this code is." A personal Jira token carries the person's full account rights; only the tool's code limits it to searching. If the agent holds the token, the read-only promise is gone. Behind the access interface the token stays with the tool, and the tool is the only thing that can use it.
      
    
      Resources already have rules, and a tool maps to one resource. The eLog decides which experiments you can read, Jira which projects, Unix groups decide who opens the DAQ log index, and IOC access security decides who writes a PV. A tool can enforce exactly that rule for exactly that resource. An application-level check would be a second, hand-copied policy per application, and it would drift. For pief's eLog, those rules live in one service, pief-authz, which the interface could ask once it is registered as a caller (Diagram 3).
      
    
      It is how EPICS already works. The CA gateway and IOC access security decide per PV, not per client program: EDM, PyDM and a Python script get the same answer for the same reported user, host and PV. Channel Access identity is asserted by the client, which is why the PV Gate proposal also leans on network isolation and a person who approves writes. This design keeps the per-resource rule and widens it from PVs to every tool, with an identity the interface has checked.
      
    
      Least privilege becomes possible. The interface can limit a session to the tools its application asked for, so a thin application with one tool can call one tool. The harness reports which application it is running, though, so that limit is a convenience. The real limit is the per-person policy at each tool, which holds whatever the application claims.

    B. EPICS PVs become one tool among many
    
      
      
      EPICS already works this way: the Channel Access (CA) gateway and each IOC's access security decide, per PV, who may read or write, whatever client program asks. The PV Gate proposal (reference 2) builds on that for agents, with a read lane for PVs (a read-only gateway for CA and PVA, EPICS's newer PV Access protocol, plus the archiver that stores PV history) and a write lane where propose_put becomes a request an operator approves. Replace "PV" with "tool call" and the same gateway covers the eLog, Jira, the DAQ logs and Slurm.

    D. The expert path: run the harness where everything is already reachable
    
      
      
      An expert can skip the interface: run the harness on an S3DF interactive node, which already reaches the eLog, Jira, Confluence, the group-readable databases and Slurm as your own account. The skills' shell commands work there as they are. This is how claude-lcls and Cogito sessions on such a node run today. There is no propose lane here: a write tool writes as you.
      
  
      
    
      
      
      What it keeps
      
      
        
        
      • Works today, with no new service.
        • 
        
      • Full shell: any script, any query, any join across the eLog snapshot tables.
        • 
        
      • The fastest loop for building and testing a new tool or feature.
        • 
      
      
    
      
    
      
      
      What it gives up
      
      
        
        
      • Where the harness can run. It must run on an S3DF node, or drive one over SSH, rather than call tools from anywhere.
        • 
        
      • Per-tool policy. The agent can do anything your Unix account and token files allow. A skill's "read-only" is a promise in its text.
        • 
        
      • Credential isolation. Your token files sit on the disk the agent can read, and a Jira token can do anything your Jira account can.
        • 
        
      • A per-tool audit trail. Only your transcripts and each service's own logs record what ran.
        • 
        
      • Sharing. Non-experts and visitors can't be handed this safely.
        • 
        
      • Live EPICS PVs. The interactive node sets no EPICS_CA_* or EPICS_PVA_* variables. The one documented live route is a session the person opens through psdev to a hutch DAQ host as the operator account, tunneled back to the agent. The LCLS AI-agent work behind this page keeps its own agents off hutch hosts (a rule in its resources.json catalog), though the shared experimental-hutch-python skill and Hutch Copilot do use this route.

    E. Not solved yet
    
      
      
        
      
      • The per-user runner is a new service. S3DF OnDemand starts per-user sessions after a web sign-in, a similar pattern. A launcher that can act as any user is powerful and needs S3DF admin review.
        • 
      
      • Shell-based skills (ask-slurm-s3df, DAQ logs) need fixed-command tools before they can sit behind the interface. experimental-hutch-python runs as the hutch operator account; its PV access moves to the PV Gate instead.
        • 
      
      • Who approves which write is each resource owner's call: the control-room operator on shift for a PV put, never pief; for an eLog post or a Jira comment, the person who asked or the shift lead. How the approval console learns who is on shift is open: pief cannot say.
        • 
      
      • How a fixed workflow launched from an operator GUI gets the person's session token, rather than the account the GUI runs under, is open. Without it, the check is no longer for the person asking.
        • 
        
      • How a Cogito session gets a session token for the interface is not settled. Claude Code's sign-in for remote MCP servers, through S3DF Dex, is one candidate; it needs a Dex client from SLAC IT. Today a Cogito session's home folder holds your S3DF token, which also opens pief directly.
        • 
      
      • Which hosts Cogito allows is SLAC IT's call. Today a session runs on an S3DF node you registered, so it is on the expert path; a host with no LCLS rights of its own would need IT. A GUI's Agent button also needs a way to open a Cogito session with context, which stock Omnigent does not offer.
        • 
      
      • The runner needs your S3DF token: today you get it by running s3df login in any S3DF shell, and it expires. Path b in Diagram 3 also needs pief login's token, kept in a separate cache by default. The interface would need a sign-in page that does this for you, and unattended runs need a refresh path.
        • 
      
      • EPICS PVs depend on the PV Gate, which is itself a proposal. Until it exists, the only documented live route is an operator session on a hutch DAQ host that the person opens and tunnels to the agent.
        • 
      
      • claude-lcls's model connection uses a shared team key for the SLAC AI gateway. That is separate from tool access and not covered here.
        • 
    
        
      • pief runs on its dev deployment only (pief-dev.slac.stanford.edu, reachable from SLAC networks, behind S3DF's sign-in gateway), with no date for production.
        • 
        
      • pief-authz accepts service callers only from inside its own cluster for now (pief issue #482, open), so the interface would need a checker grant and a service-account entry, and would run inside that cluster or wait for that fix.
        • 
        
      • pief's dev deployment accepts any S3DF token ("Every s3df token passes; narrows when JIT creds land."). The harness's session token needs an audience of its own, or it would also open pief directly.
        • 
        
      • Argument rules, such as a PV step limit, can't be expressed in pief-authz today: it drops the AuthZEN request context and its model has no conditions. They stay in the interface.
        • 
        
      • On the interactive node, pief login and s3df login keep separate token files by default (~/.local/state/s3df/access-token and ~/.s3df-access-token). pief reads only its own cache or S3DF_TOKEN. To share one login, point pief's S3DF_TOKEN_META at the metadata file s3df login writes, or run pief login with S3DF_TOKEN_FILE=~/.s3df-access-token. pief's README says the cache is shared; on the node it is not.

    H. Options for the access interface's back end, and why the per-user runner
    
      
      
      Per-user runner (chosen). The interface starts, or reuses, a process running as the person's Unix account on S3DF, the way S3DF OnDemand starts per-user sessions. Tokens, group-readable files and Slurm's node trust all work unchanged. Cost: a new service that manages per-user processes and token refresh. Its launcher can start a process as any user, so the launcher is itself a deputy and needs review. Unlike a service account, each tool call it runs carries one person's rights only, so its risk narrows to getting the mapping from sign-in to Unix account right.
      
      
      SSH forced command (works today). A key that can only run one dispatcher script on an interactive node, which accepts tool names from an allowlist. The author's own VM already reaches an interactive node over SSH as the author, through the S3DF login host, so it is the cheapest first step. It lacks tool discovery and single sign-on.
      
      
      Service account with a copied policy (rejected). One deployment, one policy table, no per-user processes. But the service would hold everyone's rights at once, a confused deputy, and the eLog tool explicitly refuses a shared-account fallback.
      
      
      Kerberos delegation (rejected as the only answer). It could carry identity to HTTP services, but not to Unix file permissions or Slurm.
      
    
      
  
      

      
    I. Glossary
    
      
      
      S3DF: SLAC's shared compute and data facility. People log in to its interactive nodes.
      
      
      claude-lcls: Claude Code configured for the SLAC AI gateway, with the shared LCLS skills.
      
      
      Cogito: SLAC IT's hosted agent service, built on the Omnigent server; it runs Claude Code sessions on S3DF interactive nodes, and loads the same skills once your ~/.claude-lcls is linked into its per-host home.
      
      
      MCP: Model Context Protocol, the standard way a harness discovers and calls remote tools.
      
      
      PV, CA, IOC, ASG: an EPICS process variable; Channel Access, the network protocol for PVs; the I/O controller that serves them; the access security group rules an IOC checks.
      
      
      AI4SO: SLAC's AI for Science and Operations department, author of the roadmap one-pager.
      
      
      AMI, DAQ, PCDS: LCLS's online monitoring program; the data acquisition system; Photon Controls and Data Systems, the LCLS group whose controls network holds the hutch hosts and IOCs.
      
      
      Access interface: this page's proposed front door for all tools (the generic pattern is called an agent gateway in reference 3). PV Gate: the proposal in reference 2 for EPICS PVs, a read-only CA gateway plus operator-approved writes. CA gateway: EPICS's existing Channel Access gateway program.
      
      
      pswww, psdev, munge, milano: the LCLS web services host behind the eLog API; the jump host into the hutch network; the service Slurm uses to trust a node's user identity; an S3DF CPU partition.
      
      
      Omnigent, Osprey, epics-mcp: the open-source agent server from Databricks that Cogito runs; an EPICS agent toolkit from Berkeley Lab's ALS; SLAC's read-only EPICS MCP server. The last two are compared in reference 5 and fitted to pief in Appendix M.
      
      
      PV area: a group of one hutch's PVs, the unit a new pief-authz type would grant (the mockup's pv_area). pief-authz does not have it today.
      
      
      Confused deputy: a service that holds many people's rights and can be tricked into using one person's rights for another.
      
      
      Enforcement point, decision point: the part that lets a call through or stops it (here the access interface), and the service it asks for the answer (pief-authz). AuthZEN is the standard question between the two.
      
      
      Front end: what a person uses to reach agent work. A terminal or Cogito's web page connects to an agent session. A GUI's Agent button either connects the person to Cogito or launches a fixed workflow; it never starts a harness of its own.
      
      
      Workflow engine, LangChain: the runtime for a fixed workflow. LangChain is a library for chaining model calls and tools into a fixed pipeline; a saved workflow run headless by Claude Code or opencode works the same way.
      
      
      Open-ended agent, fixed workflow: an application where the model picks the next tool (bringing tools to the AI), versus one where the code fixes the steps and a model fills one of them (bringing AI into a tool). Reference 11 calls these agents and workflows.
      
      
      eLog grubber: an existing LCLS operator application named in the roadmap (spelled "eLog grabber" there). Its candidate agent would answer questions about the experiment record.
      
      
      Grafana, ConfigDB, LUTE: the dashboard and metrics service; the DAQ configuration database; an LCLS analysis-workflow framework. The roadmap lists all three as tools.
      
      
      pief-authz, pief: SLAC's new authorization service (OpenFGA behind the AuthZEN API), proposed here as the interface's decision point; and the new eLog (logbook) it was built with, plus a read-only CLI. Both run on a dev deployment only (Appendix L).
      
      
      S3DF Dex: S3DF's sign-in service (OpenID Connect). s3df login and pief login get a token from it with a device flow, a code you confirm in a browser.
      
      
      OpenFGA, AuthZEN: an open-source authorization engine that stores relationships, such as who reads which logbook, and answers checks; and the OpenID standard API for asking "may this subject do this action on this resource?" (references 13 and 14).
      
      
      Cutover: the planned switch from the legacy eLog to pief's logbook. Until then, pief's logbook takes no writes.
      
      
      RAG: retrieval-augmented generation, a fixed pipeline that fetches documents and then asks a model about them.
      
      
      Goal campaign: many agents working toward one checkable goal. A main agent works through a written contract in iterations, delegating to planner, worker, skeptic and cold-reader agents (reference 7). It is a way to scale up agent use, not an application; behind the interface, every one of those agents would call the same checked tools.
      
      
      Personal access token: a per-person secret a service issues (Jira, Confluence). The page names where tokens live, never their values.
      
    
      
  
      

      
    J. A second eLog tool, and a rule the tool layer can narrow
    
      
      
      elog-copilot answers eLog questions with SQL over a snapshot of the whole eLog instead of the live API. The diagrams leave it out to keep one eLog tool in view.
      
      
      The eLog snapshot behind elog-copilot is fetched with one owner's Kerberos identity, not the reader's, so any member of its Unix groups can read every experiment in it, past the eLog's own per-experiment rule. A tool behind the interface knows who is asking and can filter its answers to the experiments that person can read in the eLog, for every call that comes through the interface. A feature can only ask for that in text. Group members can still open the file directly, so the full fix is upstream: a per-person snapshot, or the live eLog through elog-search.

      Is pief-authz needed here? our answer
      
    
        
      
      • Yes, as the interface's decision point. pief-authz holds who may read or post each pief logbook and answers over a standard API (AuthZEN); with new types it would answer for PV areas and for using each tool. In the propose lane it turns away a post that pief's roles do not allow, before anyone is asked. Until cutover it is an early check, not the final word, for reads and posts alike: the legacy eLog still decides with its own roles, which differ from pief's in places (pief drops some site-wide read and post rights).
        • 
      
      • For PVs, a natural home, with new work on both sides. SLAC's epics-mcp already checks every PV read per user and per PV, against a policy file by default or against OpenFGA, the engine under pief-authz, so pief-authz could hold those grants. That needs a PV type in pief, an AuthZEN client in epics-mcp and pief's open caller issue fixed. Osprey has no per-PV grants; it fits as the write service, whose limit, step and readback checks run after the control room approves. Neither asks pief who approves a put (Appendix M).
        • 
      
      • Not for the agent's call. pief-authz has no tool rules (catalog, lanes, argument limits), approval step or decision log. Those stay in the interface, and each resource's own rules still apply underneath.
        • 
      
      • pief's logbook takes no writes yet. It rejects every write until it replaces the legacy eLog, so an approved eLog post still goes to the legacy eLog, as the person.

      Where it sits. Behind the interface, epics-mcp fits best inside the per-user runner over stdio, with EPICS_STDIO_USER set from the verified token for its own per-PV check (config.py 13). Because the runner runs as the person's Unix account, its reads would reach the gateway under that account. Its HTTP service reads through one shared client as its own service account (epics_client.py 44–56; Dockerfile 31, 43). It is read-only for now, "read-only first" (todo/001 38–40), so a PV put still takes the propose lane, the control room's approval and the write service.
      
      
      A correction to reference 5. Its trusted-proxy mode, which takes the user name from a header, exists only when JWT checking is switched off (middleware.py 9–16, 206–238). With JWT on, there is no header fallback.

      Verdict. Osprey is a whole stack: its own web sign-in, a Claude Code container per person, skills and several MCP servers, so it fills all four layers by itself. With pief it plays best as a tool behind the interface: its controls server, run over stdio, could be the write service that sends a put after the control room approves, keeping its own limit, step and readback checks. As the front door it would duplicate the interface, and it keeps no token to show pief, only a name.
